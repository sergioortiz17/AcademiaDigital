# Evidencia M11 — recibos digitales

**Fecha:** 2026-08-24

**Estado:** MVP completado y validado sobre SQL Server Docker.

## Alcance implementado

- Emisión automática de un recibo interno no fiscal por cada nuevo pago confirmado.
- Serie global `REC-00000001`, reservada bajo transacción serializable y lock de la secuencia singleton.
- Integración atómica con confirmación de efectivo/tarjetas y con conciliación aprobada de transferencias.
- Snapshot inmutable de institución, alumno, DNI, conceptos, monto, fecha, operador y medio de pago.
- PDF local-first, almacenamiento durable, SHA-256 verificado en descarga y generación reintentable sobre el mismo número.
- Ledger sin borrado; una reversión de pago preserva el comprobante histórico.
- Campos opcionales `FiscalCae` y `FiscalQrData` para una integración futura fuera del MVP.
- Historial y descarga para Admin/Tesorería y para el alumno propietario.
- Backup/restore coordinado de SQL Server y del volumen de archivos documentado en `docs/BACKUP_RECEIPTS.md`.

## API agregada

Se incorporaron 5 operaciones:

- `GET /api/v1/receipts?studentId=...`
- `GET /api/v1/receipts/{publicId}`
- `POST /api/v1/receipts/{publicId}/generate`
- `GET /api/v1/receipts/{publicId}/download`
- `GET /api/v1/students/me/receipts`

El listado global y la regeneración requieren Admin. Detalle y descarga admiten Admin o alumno propietario. La identidad de la consulta propia se deriva de la sesión y no de un identificador enviado por el cliente.

## Persistencia y concurrencia

La migración `20260824165321_AddDigitalReceipts` agrega `Receipts` y `ReceiptSequences`. La regresión verificó dos tablas, dos claves foráneas restrictivas, tres constraints, cuatro índices únicos, el singleton inicial y los dos campos fiscales opcionales, sin crear recibos para pagos históricos durante el upgrade.

La reserva ocurre dentro de la transacción del pago, después de bloquear y aplicar las deudas. La actualización de la secuencia usa `UPDLOCK/HOLDLOCK`; un rollback revierte tanto el pago como el correlativo. El PDF se materializa después del commit: si falla, el recibo queda `Failed` y se reintenta con la misma reserva. Así no se duplica el comprobante ni se pierde su lugar lógico en el ledger.
