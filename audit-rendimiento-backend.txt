[N+1] CareerService.GetAllAsync() - 1 COUNT por carrera
  Archivo: backend-dotnet\src\AcademiaDigital.Application\UseCases\Careers\CareerService.cs
  Líneas: 25-35
  Problema: foreach sobre todas las carreras, cada iteración ejecuta
            courseRepository.CountByCareerIdAsync(career.Id).
            Con 20 carreras = 21 queries (1 GetAll + 20 COUNT).
  Fix: Hacer un solo query agrupado que devuelva Dictionary<int, int> con
       careerId → courseCount. Algo como:
       SELECT career_id, COUNT(*) FROM courses GROUP BY career_id

[N+1] GradebookRepository.SaveGradeRevisionsAsync() - 1 query por revisión
  Archivo: backend-dotnet\src\AcademiaDigital.Infrastructure\Persistence\Repositories\GradebookRepository.cs
  Líneas: 105-118
  Problema: foreach sobre cada revisión, cada iteración hace un query para buscar
            la versión anterior (WHERE evaluationId = X AND enrollmentId = Y ORDER BY version DESC).
            Con 30 alumnos × 5 evaluaciones = 150 queries individuales.
  Fix: Pre-cargar todas las revisiones actuales de una vez con un solo query
       filtrado por los pares (evaluationId, enrollmentId) que vienen en el batch,
       y luego hacer el lookup en memoria.

[N+1] GradebookRepository.ApplyFinalResultsAsync() - 1 SELECT FOR UPDATE por enrollment
  Archivo: backend-dotnet\src\AcademiaDigital.Infrastructure\Persistence\Repositories\GradebookRepository.cs
  Líneas: 123-137
  Problema: foreach sobre resultados, cada iteración ejecuta
            SELECT * FROM "Enrollments" WHERE id = {result.EnrollmentId} FOR UPDATE
            Con 30 alumnos = 30 queries con lock individual.
  Fix: Hacer un solo SELECT ... WHERE id IN (...) FOR UPDATE para lockear
       todos los enrollments de una vez, y luego iterar en memoria.

[N+1] ExamTableRepository.SaveGradeRevisionsAsync() - 1 query por revisión de examen
  Archivo: backend-dotnet\src\AcademiaDigital.Infrastructure\Persistence\Repositories\ExamTableRepository.cs
  Líneas: 116-129
  Problema: Mismo patrón que GradebookRepository.SaveGradeRevisionsAsync().
            foreach con query individual para buscar versión anterior por ExamRegistrationId.
  Fix: Mismo approach: pre-cargar revisiones actuales en un solo query.

[N+1] EnrollmentPeriodHandlers - GetPeriodDivisionCoverageQueryHandler
  Archivo: backend-dotnet\src\AcademiaDigital.Application\UseCases\Enrollments\EnrollmentPeriodHandlers.cs
  Líneas: 344-354
  Problema: Loop anidado foreach(year) × foreach(shift), cada iteración ejecuta
            commissionRepository.FindMatchingActiveAsync().
            Con 5 años × 3 turnos = 15 queries individuales.

[N+1] CourseSectionHandlers.ReattachUnmatchedEnrollmentsAsync()
  Archivo: backend-dotnet\src\AcademiaDigital.Application\UseCases\Teachers\CourseSectionHandlers.cs

[N+1] PaymentRepository.LockDebtsForPaymentAsync() - ReloadAsync por cada deuda

  2.1  VULNERABILIDAD: Reset token expuesto en respuesta HTTP
════════════════════════════════════════════════════════════════════════════════

[CRÍTICO] AuthController.ForgotPassword devuelve el resetToken al caller
  Archivo: backend-dotnet\src\...\Controllers\AuthController.cs, línea 82
  Código:  return Ok(new { success, resetToken = result.ResetToken, msg = "..." });
  Problema: Cualquier persona puede llamar POST /api/v1/users/forgot-password
            con cualquier email y recibir el token de reset en la respuesta.
            Con ese token puede resetear la contraseña de cualquier cuenta.
  Fix: El resetToken debería enviarse por email, NUNCA devolverse en la respuesta.
       La respuesta debería ser siempre el mismo mensaje genérico sin el token.

[ALTO] Token de acceso con expiración de 7 días
  Archivo: backend-dotnet\src\...\Services\JwtTokenService.cs, línea 16
  Problema: Un access token válido por 7 días es excesivo. Si se filtra,
            el atacante tiene una semana entera de acceso.

[ALTO] Sin validación de Issuer ni Audience
  Archivo: backend-dotnet\src\...\Services\JwtTokenService.cs, líneas 49-50

════════════════════════════════════════════════════════════════════════════════
  3.1  Sin health checks
════════════════════════════════════════════════════════════════════════════════

[CRÍTICO para cloud] Ni el monolito ni Finance tienen health check endpoints
  Problema: Kubernetes, ECS, App Service, etc. necesitan endpoints de
            liveness (/health/live) y readiness (/health/ready) para:
            - Saber cuándo reiniciar un pod que está colgado
            - Saber cuándo empezar a enrutar tráfico después de un deploy
            - Escalar automáticamente
  Fix: Agregar app.MapHealthChecks() con checks de:
       - Liveness: el proceso responde (básico)
       - Readiness: la DB está accesible
       Paquete: Microsoft.Extensions.Diagnostics.HealthChecks
                AspNetCore.HealthChecks.NpgSql


════════════════════════════════════════════════════════════════════════════════
  3.2  Sin response compression
════════════════════════════════════════════════════════════════════════════════

[ALTO] Ningún servicio comprime respuestas
  Problema: Las respuestas JSON (listas de alumnos, planillas, deudas) se
            envían sin comprimir. En cloud cada byte de egress cuesta.
            Un JSON de 500KB se reduce a ~50KB con gzip.
  Fix: Agregar en ambos servicios:
       builder.Services.AddResponseCompression(options => {
           options.EnableForHttps = true;
           options.MimeTypes = ResponseCompressionDefaults.MimeTypes;
       });
       app.UseResponseCompression(); // antes de UseStaticFiles/MapControllers


════════════════════════════════════════════════════════════════════════════════
  3.3  Sin HTTPS redirection
════════════════════════════════════════════════════════════════════════════════

[ALTO] Ni UseHttpsRedirection() ni UseHsts() en ningún servicio
  Archivos: Ambos Program.cs
  Los Dockerfiles configuran solo HTTP (http://+:8000, http://+:8091).
  Problema: Si TLS termina en el load balancer pero alguien hace una
            request HTTP directa al backend, viaja sin cifrar.
  Fix: En producción, agregar UseHttpsRedirection() o al menos
       configurar el reverse proxy / load balancer para que rechace HTTP.
       Agregar header Strict-Transport-Security (HSTS).


════════════════════════════════════════════════════════════════════════════════
  3.4  Índice faltante en ActiveSessions.Token
════════════════════════════════════════════════════════════════════════════════

  Archivo: backend-dotnet\src\...\Configurations\ActiveSessionConfiguration.cs

════════════════════════════════════════════════════════════════════════════════
  3.6  Docker: containers corren como root
════════════════════════════════════════════════════════════════════════════════

[MEDIO] Ambos Dockerfiles (.NET) no tienen directiva USER
  Archivos: backend-dotnet\Dockerfile, services\...\Dockerfile
  Problema: Los containers corren como root, lo cual es una violación de
            seguridad básica en cloud. Si un atacante compromete el proceso,
            tiene acceso root al container.
  Fix: Agregar antes del ENTRYPOINT:
       RUN adduser --disabled-password --no-create-home appuser
       USER appuser


════════════════════════════════════════════════════════════════════════════════
  3.7  Sin connection pool tuning ni EnableRetryOnFailure
════════════════════════════════════════════════════════════════════════════════

[MEDIO] Connection strings sin configuración de pool
  Archivos: Ambos appsettings.json
  Problema: Sin MaxPoolSize, MinPoolSize, Connection Lifetime configurados.
            El default de Npgsql es MaxPoolSize=100, lo cual puede ser
            demasiado para un cloud con múltiples réplicas (100 × N réplicas
            = muchas conexiones abiertas al PostgreSQL).
  Fix: Agregar a la connection string:
       ;Pooling=true;MinPoolSize=5;MaxPoolSize=20;Connection Idle Lifetime=300

[MEDIO] Sin EnableRetryOnFailure para errores transitorios en runtime
  Archivos: DependencyInjection.cs (ambos servicios)
  Problema: Solo hay retry en startup. En runtime, un error de red transitorio
            falla inmediatamente sin reintentar.
  Fix: En AddDbContext, agregar:
       options.UseNpgsql(conn, npgsqlOptions =>
           npgsqlOptions.EnableRetryOnFailure(3, TimeSpan.FromSeconds(1), null));

════════════════════════════════════════════════════════════════════════════════
  3.9  Sin logging estructurado

  Archivos: backend-dotnet\src\...\Services\HttpFinanceClient.cs

════════════════════════════════════════════════════════════════════════════════
  3.13  Archivos en memoria completa (sin streaming)
════════════════════════════════════════════════════════════════════════════════

[BAJO] LocalFileStorage materializa archivos completos en memoria
  Archivo: backend-dotnet\src\...\Services\LocalFileStorage.cs
  Línea 31: content.ToArray() — materializa todo el contenido
  Línea 49: File.ReadAllBytesAsync — carga archivo entero en RAM
  Problema: Si alguien sube un archivo grande, consume toda la RAM del pod.
            En cloud con pods de 256-512MB RAM, esto puede crashear el proceso.
  Fix: Usar streaming con FileStream en vez de byte[] completo.
       Para PDFs (certificados, recibos) el tamaño actual es chico y aceptable.


════════════════════════════════════════════════════════════════════════════════
  3.14  Sin HTTP caching headers para endpoints de lectura
════════════════════════════════════════════════════════════════════════════════

[BAJO] Ningún endpoint usa Cache-Control ni ETags
  Problema: Endpoints de catálogos (carreras, materias, métodos de pago) que
            cambian muy poco se consultan siempre contra la DB.
  Fix: Agregar [ResponseCache(Duration = 300)] en endpoints de catálogos,
       o implementar ETag con un middleware para evitar transferir datos
       cuando no cambiaron.


════════════════════════════════════════════════════════════════════════════════
  3.15  EF Core: Log de SQL con parámetros sensibles
════════════════════════════════════════════════════════════════════════════════

[BAJO] SQL logging incluye parámetros en Development
  Archivo: backend-dotnet\src\...\appsettings.Development.json, línea 6
  Config:  "Microsoft.EntityFrameworkCore.Database.Command": "Information"
  Problema: Esto logea TODAS las queries SQL incluyendo parámetros,
            que pueden contener datos sensibles (DNI, passwords hasheados).
            Si este nivel se activa accidentalmente en producción, filtra PII.
  Fix: Asegurar que en producción sea "Warning" o superior.
       Idealmente usar EnableSensitiveDataLogging(false) explícitamente
       en producción (es false por default, pero hacerlo explícito).
